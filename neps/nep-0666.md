## Summary

This standard defines a common view interface for contracts that verify NIST post-quantum signatures: ML-DSA-87 (FIPS 204), SLH-DSA-SHAKE-256s (FIPS 205) and a dual mode that requires both. Each method takes hex-encoded inputs and returns a four-valued result compatible with the panic-free contention standard, so a caller can combine signature checks with other evidence by the same rule. The interface lets wallets, DAOs, bridges and agents ask any conforming contract "is this post-quantum signature valid?" without depending on one implementation, and it works today in ordinary contract Wasm without protocol changes. A live implementation exists on mainnet.

## Motivation

Signatures that must stay valid for decades (identity keys, DAO charters, release signing, settlement batches, bridge attestations) are exposed to future quantum attacks on elliptic-curve schemes. NIST has standardised ML-DSA (lattice-based) and SLH-DSA (hash-based) for this purpose. NEAR contracts can already verify them in Wasm, at a measurable gas cost, but each team that does so invents its own method names, encodings and error behaviour. [NEP-645] adds ML-DSA-65 access keys and transaction signatures at the protocol level and records on-chain verification host functions as a later milestone; [NEP-646] adds FIPS 202 SHA-3 host functions. This proposal is complementary: it defines the *contract-level* interface by which one contract asks another (or itself) to verify a post-quantum signature over arbitrary data, so that DAOs, bridges and agents can rely on post-quantum attestations now, and so that future host functions have an established interface to sit behind.

A standard interface:

- lets a contract delegate verification to any conforming verifier, or embed one, interchangeably;
- gives agents and indexers one shape to call and to read;
- makes the dual mode, where a signature stays valid if either the lattice or the hash assumption survives, a recognised option for long-lived anchors;
- defines fail-closed behaviour for malformed input.

## Specification

### Algorithms and sizes

| Method | Algorithm | Public key | Signature |
|---|---|---|---|
| `mldsa87_verify` | ML-DSA-87, FIPS 204 | 2,592 bytes | 4,627 bytes |
| `slhdsa256s_verify` | SLH-DSA-SHAKE-256s, FIPS 205 | 64 bytes | 29,792 bytes |
| `pqm_verify` | both of the above | both keys (proposed: concatenated, ML-DSA first; see Unresolved Issues) | both signatures (same layout) |

Verification follows the pure (non-pre-hash) signing modes of FIPS 204 and FIPS 205 with an optional context string of at most 255 bytes.

### Interface

All methods are view methods and MUST NOT write state.

```
mldsa87_verify{pk, sig, msg, ctx?}    -> {"state": "TRUE" | "FALSE" | "NEITHER", "code": 1 | 2 | 0}
slhdsa256s_verify{pk, sig, msg, ctx?} -> same
pqm_verify{pk, sig, msg, ctx?}        -> same
```

- `pk`, `sig`, `msg` and `ctx` are lowercase hexadecimal strings.
- `TRUE` (`code` 1): the signature verifies under the key, message and context.
- `FALSE` (`code` 2): the inputs are well formed and the signature does not verify.
- `NEITHER` (`code` 0): the inputs are malformed (wrong length, invalid hex, context longer than 255 bytes). Implementations SHOULD return `NEITHER` rather than panic, so that callers combining results never mistake malformed input for a verdict.
- `pqm_verify` returns `TRUE` only if both component signatures verify; it returns `FALSE` if either is well formed and fails.

### Composition

Results are four-valued states (`NEITHER 0`, `TRUE 1`, `FALSE 2`; `BOTH 3` is reserved for combined evidence) and MAY be combined with other evidence using the chain meet of the panic-free contention standard. A contract MUST authorise an action only on `TRUE`.

### Domain separation

Callers SHOULD sign a domain-separated message that includes the contract account, the method or action, the signer's account and a nonce, so that a signature cannot be replayed against a different contract, action or account.

### Optional metadata

A conforming contract MAY expose `pq_verify_metadata{}` returning the supported methods, the standards and versions implemented, and the measured gas per method.

## Reference Implementation

`scp144.near` (NEAR mainnet, zero access keys, so the code cannot change) implements the three methods in freestanding C compiled to Wasm. Its on-chain ABI is readable with the free view `abi{}`.

- Project measurements: about 7.4 TGas for `mldsa87_verify` and about 53.6 TGas for `slhdsa256s_verify`.
- A well-formed but invalid signature returns `{"state":"FALSE","code":2}`.
- **Deviation from this draft:** inputs of the wrong length currently cause a contract panic rather than a `NEITHER` result. A conforming wrapper, or a new deployment, would implement the `NEITHER` behaviour.

The implementation is tested against NIST ACVP vectors. It has not been certified by NIST CMVP, and certification is not implied by this standard.

## Security Implications

- **Implementation correctness.** A verifier that accepts an invalid signature defeats the purpose. Implementations should pass the NIST ACVP and known-answer vectors and should be reviewed independently. Constant-time behaviour matters less for verification than for signing, but malformed-input handling must be strict.
- **Gas cost as a limit.** SLH-DSA verification is expensive; callers must attach enough gas and should not loop over many verifications in one call.
- **Upgradeability.** A verifier whose code can change could be altered to accept forgeries. Callers should prefer verifiers with no access keys, or pin a verifier by code hash.
- **Replay.** The interface verifies signatures only; preventing replay is the caller's responsibility (see domain separation).
- **Key distribution.** The interface does not establish who owns a public key. Binding keys to accounts is out of scope.

## Alternatives

- **Protocol host functions** for ML-DSA and SLH-DSA would be cheaper and are a natural follow-up. They require a protocol change and validator upgrade; this standard works now and gives host functions an interface to match later.
- **Per-project interfaces,** as today, which fragment tooling.
- **Pre-hash modes** (HashML-DSA, HashSLH-DSA) would reduce input size for large messages; they could be added as further methods.

## Future possibilities

- An `mldsa65_verify` method with the same conventions, so contracts can check signatures made by the ML-DSA-65 keys introduced in [NEP-645] (1,952-byte public keys, 3,309-byte signatures).
- Host functions with the same input and output conventions, following the on-chain verification milestone anticipated by [NEP-645] and reusing the SHA-3 host functions of [NEP-646] internally.
- ML-KEM-1024 (FIPS 203) public-key publication and handshake records as a companion standard.
- Wallet support for post-quantum guard keys that use this interface.
- Additional parameter sets (ML-DSA-65, SLH-DSA-SHA2 variants).

## Consequences

### Positive

- Contracts can require post-quantum signatures today through a shared interface.
- The dual mode gives long-lived anchors resilience to the failure of one family of assumptions.

### Neutral

- Callers still choose which algorithm to require and how keys are bound to accounts.

### Negative

- Verification is costly in gas compared with Ed25519.
- Multiple verifier deployments may vary in quality; callers must choose carefully.

### Backwards Compatibility

Additive. No existing contract or standard changes.

## Unresolved Issues (Optional)

- Whether to standardise the concatenation layout for `pqm_verify` or to take the two keys and signatures as separate fields.
- Whether to require `NEITHER` for malformed input (MUST) rather than recommend it (SHOULD).
- Whether metadata should report gas or leave measurement to tooling.
