## Summary

This proposal introduces **Universal Accounts**: one unified, post-quantum-safe scheme for deriving both implicit (user-created) and deterministic (contract-created) account ids, which have until now needed separate mechanisms. A universal account id (`0u...`) is the SHA3-256 hash of a `StateInit`, a small struct naming the account's code, storage, and access keys. Which of those fields are populated determines what the account is: a key-only externally-owned account, a contract, or both. This is the first account scheme that supports post-quantum implicit accounts.

Universal accounts are a new, disjoint scheme for *new* accounts only. The three existing derivations (NEAR-implicit, ETH-implicit, and [NEP-616]'s deterministic `0s` accounts) are untouched and keep working; there is no migration.

A universal account can be created two ways: a relayer or contract can fund and initialize it in one batch (`Transfer` + `StateInit` + optional follow-up call), or the account's own future owner can sign a transaction directly against the not-yet-existing id, self-authorizing initialization with a key the id itself commits to. Two new host functions let a contract built against this scheme derive and create accounts of a `StateInit` version that did not exist when the contract was compiled, closing the same forward-compatibility gap [NEP-616]'s equivalent mechanism left open.

Universal accounts are stabilized at protocol version 87, included in the neard 2.14 release.

## Motivation

NEAR has three ways to get an account without a `CreateAccount` action: a 64-character hex NEAR-implicit id (an ed25519 public key), a `0x`-prefixed 40-hex-character ETH-implicit id (a secp256k1 public key, Keccak-hashed), and a `0s`-prefixed deterministic id ([NEP-616]), hashed from a `StateInit` of mandatory code plus optional data. Each solves one problem: an implicit id lets a wallet start using a key before touching the chain; a deterministic id lets a contract predict and initialize an account it has never seen, enabling sharded contract designs.

None of the three is quantum-safe. [NEP-645] added ML-DSA-65 as a transaction-signing scheme for existing named accounts, but explicitly left implicit-account derivation out of scope: a 32-byte post-quantum key handle does not fit the legacy 40-hex-character or `0s` formats, and the problem was judged to deserve its own design rather than a cramped extension. This proposal is that design, and it goes further than adding a fourth format: it collapses "implicit" and "deterministic" into one scheme, because the distinction between them was never load-bearing. An account is defined by what state it will hold on first use; whether a human or a contract supplies that state does not change what the id needs to guarantee.

[NEP-616] also has a narrower, separate forward-compatibility problem this proposal avoids repeating: an immutable or already-deployed contract that builds a `StateInit` value at compile time can never construct a *new* variant of that type added after it shipped. Sharded fungible token wallets and other global-contract-based designs are exactly the immutable contracts most likely to need to keep creating accounts of a `StateInit` shape added after they were deployed. This is a forward-looking property, not a retrofit: it protects a contract built against this scheme today from a future `UniversalStateInit` version, the same way it would have protected a [NEP-616]-based contract from a future `DeterministicStateInit` version, had one existed. It does not, on its own, let an existing `0s`-based contract create `0u` accounts; that requires the contract to adopt this scheme in the first place. Universal accounts solve the forward-looking version of the problem by making the wire representation of `StateInit` opaque bytes, with new host functions that derive an id and create an account from those bytes without the calling contract ever needing to understand their structure.

Finally, no migration is proposed for any existing account, and legacy schemes are not being deprecated. Every wallet, exchange, and contract that already generates NEAR-implicit, ETH-implicit, or `0s` addresses keeps working exactly as before. Representing an existing account of any of those three kinds as an equivalent `0u` id was also considered and set aside, not adopted (see [Alternatives](#alternatives)): it is not obvious that two different derivations naming the same account means anything useful, and it would only add another choice every wallet has to reason about at key-generation time, for no compensating benefit.

## Specification

The keywords "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

A single protocol feature, `ProtocolFeature::UniversalAccounts`, gates the entire scheme. It is stabilized at protocol version 87.

### Address format

A universal account id is the two-character prefix `0u` followed by 52 lowercase [Crockford base32](https://www.crockford.com/base32.html) symbols encoding a 256-bit SHA3-256 hash, MSB-first, 5 bits per symbol, with the final symbol's 4 unused bits set to zero. The full id is 54 characters, well within the 64-character `AccountId` limit.

```
0u | 52 symbols encoding SHA3-256(RawStateInit bytes)
```

The address carries **no checksum**. An earlier design added one (see [Alternatives](#alternatives)); it was removed before stabilization because it could not be safely enforced.

The only validity rule on the string itself is canonicity of that final symbol: with 260 bits of symbol capacity carrying a 256-bit hash, only 2 of the 32 possible final symbols (`0` and `g`) have their trailing 4 bits zero. A string with any other final symbol, or that otherwise does not match this shape, is not a universal account id; it is classified as an ordinary named account instead. This canonicity rule is enforceable (the prefix and length are the protocol's own choice) and is unrelated to the `StateInit`-content canonicity question discussed below.

Classifying a string as a universal account id (`AccountType::UniversalAccount`) is implemented in the `near-account-id` crate, alongside the other account-type predicates, not in nearcore itself.

### `StateInit`

`StateInit` names everything an account needs to become usable:

```rust
pub enum UniversalStateInit {
    V1(UniversalStateInitV1),
}

pub struct UniversalStateInitV1 {
    /// Contract code, by reference to a global contract. Absent for a key-only account.
    pub code: Option<GlobalContractIdentifier>,
    /// Storage entries to populate on initialization.
    pub data: BTreeMap<Vec<u8>, Vec<u8>>,
    /// Access keys to install, all full-access (see Keys, below).
    pub access_keys: BTreeSet<PublicKeyHandle>,
}
```

`GlobalContractIdentifier` is the type [NEP-591] introduced for referencing global contract code by hash or by account id. `PublicKeyHandle` is the on-trie key representation introduced alongside [NEP-645]: for a classical key it is the key itself; for an ML-DSA-65 key it is a 32-byte, domain-separated SHA3-256 hash of the 1952-byte public key, so committing a post-quantum key to a `StateInit` costs no more than a classical one.

There is deliberately no separate variant, tag, or field for "kind": whether an account is a key-only externally-owned account, a contract, or both is entirely determined by which of `code`, `data`, and `access_keys` are populated. All three MAY be empty at once; the resulting account is inert but valid, the universal-account analogue of a burn address. The `V1` wrapper is the version discriminant; a future revision adds `V2` rather than changing `V1`'s fields, so an id derived under one version never collides with one derived under another.

On the wire and in the `UniversalStateInit` action, this value never appears in its typed form. It is carried as:

```rust
pub struct RawStateInit(pub Vec<u8>);
```

an opaque byte string holding the canonical borsh encoding of a `UniversalStateInit` value. `RawStateInit` itself is borsh-serializable, since it needs to travel as a field of the `UniversalStateInit` action, but that outer encoding (which prepends its own length prefix) is irrelevant to the account id: the id hashes `self.0` directly, never the result of borsh-serializing the `RawStateInit` wrapper. An earlier version conflated the two and hashed the wrong bytes; see [Derivation](#derivation), just below, for how the current design avoids it.

#### Derivation

An account's id is:

```
0u-encode( SHA3-256( raw_state_init.0 ) )
```

always computed over the **exact bytes supplied**, never over a re-serialization of a decoded value. This is a strict requirement, not an implementation detail: if the runtime ever decoded a `RawStateInit` and re-derived an id from re-encoding the decoded value, a value whose original bytes were not in canonical borsh form (unsorted map keys, for instance) would silently derive a *different* id than the one it was actually addressed to. Two independent code paths enforce this: the `UniversalStateInit` action's receiver check runs against the raw bytes before any decode is attempted, and the account-id-derivation host function (below) is defined directly over the byte string it is given, with no decode step at all.

#### Content canonicity is not enforced

A `RawStateInit` byte string that decodes successfully but is not the canonical borsh encoding of its own decoded value (for example, a `data` map whose keys are not in sorted order) is **accepted**, not rejected. It simply derives a different id than the canonical encoding of the same logical value would. This was implemented as a rejected case in an earlier version and then deliberately relaxed (see [Alternatives](#alternatives)): the protocol can only ever see and canonicalize the outer `StateInit` container, never bytes a contract has independently serialized into one of its own `data` values, so a guarantee of "same-looking `StateInit` always hashes the same" was never something the protocol could fully keep, and asserting it in the one place it could be checked bought nothing.

Producers of a `StateInit` (wallets, SDKs, contracts) are responsible for serializing consistently if they want a reproducible id; the reference Rust encoding is canonical by construction (its containers are `BTreeMap`/`BTreeSet`), but nothing prevents a different encoder, in a different language, from producing a different, equally valid id for the same logical content.

### The `UniversalStateInit` action

```rust
pub struct UniversalStateInitAction {
    pub state_init: RawStateInit,
    pub deposit: Balance,
}
```

This creates or continues initializing the account at `state_init`'s derived id, which MUST equal the receipt's receiver. Validation, in order:

1. The receiver id MUST equal the id derived from the raw bytes (checked before any decode; failure is `InvalidUniversalStateInitReceiver`).
2. The bytes MUST decode as a `UniversalStateInit` (failure is `MalformedUniversalStateInit`, at both validation and action-error level, so it can be produced whether the check runs ahead of execution or the malformed bytes reach the runtime handler directly).
3. Each storage key and value MUST NOT exceed the ordinary storage-write length limits (`max_length_storage_key` = 2048 bytes, `max_length_storage_value` = 4 MiB); there are no separate, universal-account-specific length limits.
4. The total number of `access_keys` committed across every `UniversalStateInit` action in the same receipt MUST NOT exceed `max_universal_state_init_keys` (1024).
5. The total number of storage entries across every `DeterministicStateInit` and `UniversalStateInit` action in the same receipt MUST NOT exceed `max_state_init_entries` (1500, from protocol version 87 onward; effectively unbounded before, when only `DeterministicStateInit` existed). This limit is shared with the older, unrelated `0s` action; see [Security Implications](#security-implications) for why.

Rules 4 and 5 are both receipt totals, not per-action limits, and both recurse into any `Delegate`/`DelegateV2` inner actions. Every action in a receipt shares one receiver, and a state init has to derive to that receiver, so a receipt can carry many byte-identical copies of the same payload and pays for each one; a per-action bound would therefore bound nothing. The two counts are taken from a single decode of each action so that they cannot drift apart again.

If the target account does not yet exist, or exists but is uninitialized, applying the action installs `code` (via the same global-contract-reference mechanism [NEP-591] and [NEP-616] already use), writes every `data` entry, and adds every `access_keys` entry as a full-access key, all seeded with the same nonce (see [Keys](#keys)). If the account is already initialized, none of that repeats: the action only settles `deposit` against the account's storage-staking requirement, refunding any excess through the same refund-routing mechanism [NEP-616] introduced, which this action shares. This makes a repeated `UniversalStateInit` to an already-initialized account a safe no-op rather than an error, which matters for the initialization flows below.

### Account lifecycle

A universal account can be in one of three states: nonexistent, uninitialized, or initialized. This third possibility (funded but not yet initialized) is what distinguishes universal accounts from `0s` deterministic accounts, which never need it: a `0s` account's code is mandatory, so "no code yet" already means "not yet initialized," with no separate state required. A universal account's code is optional, so that trick does not work; a key-only universal account is fully initialized with no code at all, which is indistinguishable from "not yet initialized" unless the protocol tracks the distinction directly.

It does, with a dedicated account representation:

```rust
pub enum Account {
    Uninitialized(UninitializedAccountV1),
    Initialized(InitializedAccount),
}

pub struct UninitializedAccountV1 {
    amount: Balance,
    storage_usage: StorageUsage,
    bootstrap_nonce: Nonce,
}
```

`Account` is the same top-level representation every account already used before this proposal: `InitializedAccount` is what a named, NEAR-implicit, ETH-implicit, or `0s` account has always been, and what a universal account becomes once initialized. `Uninitialized` is the one variant this proposal adds, and only a universal account ever takes it.

A transfer (or any other receipt that would create an account) to a nonexistent universal account id creates it in the `Uninitialized` state, holding only balance and storage usage, plus a `bootstrap_nonce` seeded from the creating block's height. Only a `UniversalStateInit` action can move an account out of this state, by calling `initialize()`, which clears the placeholder fields and installs the real `code`/`data`/`access_keys`. Every other action that would need existing state to act on (`DeployContract`, `AddKey`, `DeleteAccount`, `FunctionCall`, `Stake`, `Delegate`, and so on) is rejected against an uninitialized account with `ActionErrorKind::AccountNotInitialized`, a distinct error from "account does not exist": the account is there, it simply has nothing installed yet. Once initialized, a universal account is deleted the same way as any other account, including one referencing a global contract; nothing about `DeleteAccount` is universal-account-specific.

The account's own actor id is never mutated as a side effect of creating it via transfer. An earlier version of the implicit-account-creation code did set it, which was harmless only because the single-action rule below made the assignment unreachable; removing that assignment, rather than relying on it staying unreachable, is what makes the batched creation flow below safe (see [Security Implications](#security-implications)).

### Creating and initializing an account

Two flows are supported.

**Relayer- or contract-funded, batched.** A `Transfer` action creating an implicit account (of any kind, including universal) is ordinarily only honored when it is the sole action in its receipt, to prevent a funder from also smuggling in an action that would seize control of the newly created account. Universal accounts are exempt from that restriction, whether the transfer, the `UniversalStateInit`, and any further actions land in one receipt or are split across receipts (for instance `[Transfer, UniversalStateInit, FunctionCall]`). This is safe specifically for universal accounts, and not for the older implicit kinds, for two reasons together: an uninitialized account is inert except for its own matching `UniversalStateInit`, so nothing else in the batch can act on it first, and the funder never becomes the account's actor. A trailing `FunctionCall` or `Transfer` succeeds normally, since neither requires its caller to be the account itself; a trailing `AddKey`, `DeleteKey`, `DeployContract`, `Stake`, or `DeleteAccount` instead fails, since all of those require the actor to equal the account, which the funder never is (see [Security Implications](#security-implications)).

**Self-signed.** The account's own future owner can also initialize it directly, with no relayer and no pre-existing access key, by signing a transaction that is addressed to the id its own state init derives to, using one of the keys that state init names in `access_keys`. The verifier recognizes this shape (`Transaction::is_state_init_bootstrap()`: signer and receiver match, a top-level action's state init derives to that id, and the signing key is among the committed keys) and authorizes the whole transaction accordingly, rather than looking up an access key that does not exist yet. Because the transaction is genuinely self-authorized, it MAY carry further top-level actions after the `UniversalStateInit`, including ones, like `AddKey` or `DeleteAccount`, that the batched flow above cannot authorize.

Because there is no access key yet, there is also no ordinary nonce to check the transaction against. The account's `bootstrap_nonce`, seeded at creation from the block height, stands in for it: the self-signed transaction's nonce MUST equal `bootstrap_nonce + 1`, checked in forced strict-nonce mode regardless of what the transaction itself requests. Exactly one nonce is admissible at a time, which is what closes a replay path a looser mode would leave open, since a failed init does not flip the account's state and the same signed bytes would otherwise stay valid indefinitely.

The nonce is consumed when the transaction passes verification, before the `UniversalStateInit` action executes, and the account keeps the consumed value. A failed init is therefore retried the ordinary way, by signing again at the next nonce; what cannot be resubmitted is the exact bytes that were already consumed. Once initialization succeeds, the installed keys' own nonces start no lower than whatever nonce a bootstrap transaction had consumed, so those bytes cannot be replayed through the ordinary access-key path either.

A `UniversalStateInit` action nested inside a `Delegate`/`DelegateV2` action does **not** qualify for self-signed authorization; only a top-level action does. A delegated action is already validated against its own, separate receiver and executes in its own receipt, so admitting it here would authorize nothing meaningful.

A separate "claim" transaction type, distinct from both of these, was proposed early in the design and rejected; see [Alternatives](#alternatives).

### Host functions

Two host functions let a contract work with universal accounts without needing to understand the internal shape of a `StateInit` it may not have been compiled against, because both operate on `RawStateInit` bytes directly:

```rust
/// Derives the account id a state-init byte string would create.
/// Total: any byte string maps to *some* id, valid state init or not.
fn universal_state_init_to_account_id(
    state_init_len: u64, state_init_ptr: u64, register_id: u64,
);

/// Appends a UniversalStateInit action to an outbound promise batch.
/// Does not check the promise's receiver against the derived id; that
/// happens at receipt validation, not at the call site.
fn promise_batch_action_universal_state_init(
    promise_idx: u64, state_init_len: u64, state_init_ptr: u64, amount_ptr: u64,
);
```

`universal_state_init_to_account_id` performs no validation and cannot fail on its input's content: it is SHA3-256 plus the address encoding, applied to whatever bytes it is given. A byte string that is not a well-formed `StateInit` simply maps to an account that no `UniversalStateInit` action can ever successfully initialize.

`promise_batch_action_universal_state_init` charges for its bytes in two stages, in a specific order, then forwards them into the created action regardless of what it finds. The size-based terms (base plus per-byte) are charged first, against whatever bytes are supplied, because reading them is the one thing every call does. The runtime then attempts its own decode, purely to compute the content-based terms (the per-entry and per-key charges described in [Fees](#fees)), and charges those only if that decode succeeds; a gas failure at either stage aborts the whole call, and an aborted call creates none of the receipts it would have, so charging size before content cannot let an attacker force an expensive decode more cheaply than reading the bytes costs. This local decode is only for pricing: whether the bytes are well-formed enough to actually install, and whether the receiver matches the id they derive to, is decided later and independently, at receipt validation.

### Keys

Every access key a `StateInit` installs is full-access; `UniversalStateInit` does not support function-call-scoped keys. This was a deliberate scope decision for the first version (see [Alternatives](#alternatives)). The format leaves room to add them later as a `V2`. That would need a protocol upgrade to gate when the new version becomes decodable, but no state migration: V1 ids, and the accounts already derived from them, are unaffected.

Keys are stored, as everywhere else in the protocol, by their on-trie `PublicKeyHandle`: the key itself for ed25519 and secp256k1, or a SHA3-256 hash of the key for ML-DSA-65. Committing a post-quantum key to a universal account therefore costs the same, in both `StateInit` size and storage staking, as committing a classical one.

### Fees

Every `UniversalStateInit` action is priced on four terms:

| Term | Charged on | Rate |
| --- | --- | --- |
| Base | the action itself | fixed |
| Per-byte | the whole raw payload, not just `data` entries | per byte |
| Per-entry | each `data` entry | 200 Ggas, execution-only, shared with `DeterministicStateInit` (see [Security Implications](#security-implications)) |
| Per-key | each `access_keys` entry | the existing `add_full_access_key` action-cost rate; no separate, universal-account-specific key fee |

Base and per-byte are anchored to the same account-creation and storage economics as the existing `DeterministicStateInit` action, not to a measured-compute estimate: an internal gas-estimator pass was run against them and its output was judged too inconsistent to anchor a fee to. Charging the per-byte term over the entire raw payload, rather than only the bytes making up `data` entries as `DeterministicStateInit`'s is, means that at equal size the universal fee can only be greater than or equal to the deterministic one.

Base, per-byte, and per-key each split into a send portion, paid by whoever creates the action (a transaction's signer at conversion, or a contract appending the promise action), and an execution portion, paid when the account is actually installed. Per-entry has no send portion at all; it is charged purely at execution. For the promise host function specifically, the send portions of base and per-byte are charged unconditionally, and the send portion of per-key only once the payload has been decoded (see [Host functions](#host-functions)).

## Security Implications

### A checksum-free address is never invalid, only nonexistent

Without a checksum, a mistyped `0u` address is still a well-formed account id. It simply names an account that almost certainly does not exist, since with a 256-bit hash, mistyping into an account that does exist is infeasible. A transfer to it therefore fails the ordinary way, as "account does not exist," and the funds are refunded.

That property is deliberate. A checksum rule could not be applied retroactively to contracts that predate it. An old contract, unaware of the rule, would accept a mistyped address and debit the sender, then hand the runtime an id the runtime now refuses. The debited funds would be stuck, with no refund path. See [Alternatives](#alternatives) for the full history.

### A `code` reference by account id is not itself content-addressed

An account's id commits to its whole `StateInit`, including which global contract `code` names, but a `GlobalContractIdentifier::AccountId` reference ([NEP-591]) is not itself immutable: the account that owns that global contract can redeploy it. A universal account's id therefore guarantees which contract it was pointed at, not which code will actually execute under that pointer over time, to exactly the same extent this already holds for [NEP-616]'s deterministic accounts. Referencing code by hash instead avoids this.

### Content-canonicity is a producer responsibility, not a protocol guarantee

Because non-canonical `StateInit` encodings are accepted rather than rejected, two byte strings that a human would consider "the same `StateInit`" (same logical fields, different container ordering) derive different ids. This is intentional (see [Alternatives](#alternatives)) but is a genuine, non-obvious footgun for any integrator who assumes the protocol enforces a single canonical encoding: it does not, beyond requiring the outer structure to decode at all. Wallets and SDKs that construct a `StateInit` themselves MUST serialize consistently (the reference Rust types already do, via `BTreeMap`/`BTreeSet`) if they want a reproducible, predictable id.

### The self-signed bootstrap nonce closes a specific replay path

Seeding `bootstrap_nonce` from the creating block's height, rather than a fixed value like zero, prevents a stale, previously-failed bootstrap transaction from a deleted-and-refunded account's earlier "incarnation" from being replayed against a newly created account at the same id; a fixed starting value would not distinguish the two.

### Removing the actor-id mutation on implicit creation

Universal accounts deliberately guard against repeating a specific mistake already made once, in [NEP-616]'s deterministic accounts: mutating a receipt's actor id as a side effect of account creation. Exempting universal accounts from the single-action rule on implicit-account-creating transfers (to permit the batched creation flow) would have reopened exactly that vector if an unrelated piece of legacy code had not also been fixed: `action_implicit_account_creation_transfer` used to unconditionally set the receipt's actor id to the newly created account, a no-op under the old single-action rule (there was never a subsequent action to authorize), but a live privilege-escalation bug the moment a subsequent action becomes possible. A relayer batching `[Transfer, UniversalStateInit, AddKey]` or `[Transfer, UniversalStateInit, DeleteAccount]` could otherwise have that trailing action authorized against the account it had just funded, installing a key the account's id never committed to, or draining it outright. The fix removes the actor-id assignment entirely, for every implicit account kind; it is provably unobserved for the older kinds because their creation gate still requires the transfer to be the receipt's only action.

### Bounding state-init size

A state init's cost scales with its contents, along two axes that ordinary action limits do not bound. Each committed access key is charged as a full `add_full_access_key` action at the send rate, burnt when the transaction converts to a receipt and prepaid by nothing. Each `data` entry carries a flat execution fee that counts toward the shard's outgoing congestion regardless of whether it is ever burnt. Left unbounded, one receipt's conversion burn can exceed `max_tx_gas`, the whole chunk's budget for converting transactions, and its entry fees can pin a shard at maximum outgoing congestion.

Both bounds MUST be receipt totals. Every action in a receipt shares one receiver, and a state init must derive to that receiver, so a receipt can carry many byte-identical copies of the same payload and pay for each one. A per-action bound therefore leaves the receipt total unbounded. Both limits are enforced by the same protocol-gated validation as the rest of this proposal, so every node applies them identically from protocol version 87 on.

A third cost is not gas-metered at all. While selecting transactions, a chunk producer decodes and hashes a candidate payload several times before any balance check can reject it. That work is bounded by the chunk producer's own transaction-preparation time limit, which is local policy rather than a protocol rule, so it protects only a producer running current software.

## Alternatives

### A checksum on the address

The address format originally included a 6-symbol checksum (a BCH polymod over the Crockford alphabet, in the style of Bech32m), bringing the total to 60 characters. It was fully implemented, known-answer tested, and agreed at a design-review meeting before being reversed, for the funds-safety reason given in [Security Implications](#security-implications). A sub-debate over which checksum algorithm to use (an off-the-shelf CRC versus the custom Bech32m-derived one) turned out to be moot once the concept of a protocol-level checksum was dropped entirely. Whether a checksum belongs at the wallet/UI layer instead, similar to TON's user-facing address format, was left an open question, not decided either way.

### Bech32(m) as the full address framing

Adopting Bech32(m) itself as the address's overall encoding, rather than only borrowing its checksum math, was rejected the same day the checksum format was proposed: it would have forced a different prefix and framing (an `hrp` plus a `1` separator) than the `0u` prefix already settled on, over a character set NEAR account ids do not otherwise share with Bech32m. Not resembling a Bitcoin-style address was treated as a feature of the `0u` format, not a gap to close.

### `StateInit` as a per-kind enum

An early design represented `StateInit` as an enum with one variant per account kind (for example `ImplicitContract` and `ImplicitMlDsa65`, each independently versioned), directly mirroring the way the two prior implicit-account kinds are structurally distinct. This was rejected in favor of one kind-agnostic struct, versioned as a whole: an account's kind is fully determined by which fields happen to be populated, and a per-kind enum would have required a new variant (and, transitively, updates to every immutable contract that matches on the enum) for every future combination of code, data, and keys, rather than just a new field.

### Splitting `StateInit` into a keyless V1 and a keyed V2

During review, whether access keys belonged in `StateInit` at all was reopened, on the argument that Wallet Contracts (existing contracts, such as those in `near/intents`, that hold a user's funds and authenticate its owner in contract logic rather than through a native access key) plus External Contract Calls (a related, later proposal for sender-less transactions; see [Future possibilities](#future-possibilities)) already give a strict superset of what a native access key provides, so adding post-quantum implicit accounts might not need one. A compromise of shipping a keyless `V1` now and a keyed `V2` later, independently protocol-feature-gated, was proposed and briefly agreed, then abandoned the same day: there was no articulable benefit to having both versions live simultaneously when `V2` is a strict superset of `V1` and would immediately replace it. The underlying "drop access keys" position was itself rejected shortly after: the team had already decided, earlier in the design, that post-quantum accounts should be first-class implicit accounts rather than a separate scheme, and dropping keys from universal accounts would have reintroduced that rejected separate scheme by another route.

### A dedicated PQ-only implicit-account scheme

Building quantum-safe implicit accounts as their own scheme, distinct from universal (deterministic-style) accounts, was proposed more than once and rejected both times, in favor of the position that motivates this whole proposal: implicit and deterministic accounts should not need two different mechanisms to both be quantum-safe.

### Representing legacy accounts as universal account ids

Giving each existing NEAR-implicit, ETH-implicit, or `0s` account an equivalent `0u` id was raised early and set aside, not formally decided against: finding an equivalence between an old and a new derivation for the same account does not obviously mean anything, and doing so would only add another format every wallet has to reason about at every key-generation or import step, for a benefit nobody could articulate. It remains open to revisit later, not permanently closed.

### Enforcing `StateInit`-content canonicity

An earlier version of the decode path rejected any byte string that was not the canonical (sorted-container) borsh encoding of its own decoded value, so that two differently-ordered encodings of "the same" logical `StateInit` could never derive two different ids. This was reverted for the reason given in [Specification](#specification): the guarantee was illusory, since a contract can always serialize its own nested collections into an opaque `data` value the protocol never inspects, so it could never be kept past `StateInit`'s own outer container anyway.

### Rejecting "unusable" state

An account with neither code nor access keys (and, in principle, no data either) was originally rejected at validation, on the reasoning that such an account could never be controlled or acted upon. This was reversed: such a state init is not meaningfully different from a `0x000...0` burn address on other chains, a legitimate way to content-address immutable data on chain with nothing that can act on it, and the validation added complexity without a matching benefit, since a state init with data but no code (equally "unusable" in the sense of having no controller) was never rejected in the first place.

### A dedicated "claim" transaction

Before self-signed initialization was designed, initializing a funded-but-uninitialized account was expected to need a distinct "claim" transaction type. This was rejected, along with the word "claim" itself: the account already belongs to whoever can produce a matching state init, by construction of the id, so nothing is being claimed, only initialized, and an ordinary (self-signed) transaction shape turned out to be sufficient once the account carried its own bootstrap nonce. A weaker authorization rule, checking only that a given state init's hash matches the account id with no signature check at all, was also considered and rejected: it would let anyone who learned a not-yet-submitted state init (for instance, an intermediary relaying it) initialize the account before its intended owner, with no way to verify the owner had actually authorized that.

### Asymmetric fee/authorization shortcuts

Two related shortcuts were proposed and rejected during the initialization-flow design. Pre-charging extra gas at account-creation time to pre-fund a fixed initialization budget, so that a later `StateInit` would need no separate authorization at all, was proposed and abandoned by its own author for requiring an arbitrary, hard-to-choose budget cap. Charging gas for a `UniversalStateInit` action against an account that is already initialized was also rejected: since such an action is otherwise a safe no-op, charging for it would let any intermediary who has seen a state init once replay it against the account repeatedly, at the account's expense, purely to grief it.

### Function-call-scoped keys in `StateInit`

Supporting anything other than full-access keys in a state init (gas keys, or function-call-restricted keys) was explicitly deferred, on the grounds that no concrete use case had been demonstrated yet and the struct's versioning already leaves room to add it later as a `V2`, at the cost of a protocol upgrade but no state migration.

### Reusing `DeterministicStateInit`'s error variants

Universal accounts define their own, parallel set of `ActionsValidationError` variants rather than reusing the existing `Deterministic*` ones, even though the underlying conditions (bad receiver, malformed payload, oversized entries) are conceptually identical. `ActionsValidationError` serializes its variant name as the JSON error tag returned over RPC, and the `Deterministic*` variants have been stable since protocol version 82; renaming or sharing them to fit a new action would be a backwards-incompatible RPC change for any client matching on those strings. A later, deliberate consolidation under neutral names is left as a follow-up, not attempted here.

## Future possibilities

- **UI-level address checksums.** Left open as a possible wallet/explorer-layer feature, distinct from and not requiring any protocol change, following precedent from other chains' user-facing address formats.
- **Function-call-scoped or otherwise restricted keys in `StateInit`.** The struct's versioning supports this as a `V2`, once a concrete need is identified: a protocol upgrade to gate the new version, but no state migration.
- **A dedicated `UNINITIALIZED_ACCOUNT` RPC status**, distinct from "account does not exist," so a client can tell the two apart without separately querying `AccountView.state`.
- **View-calls carrying an optional state-init parameter**, to let a caller inspect what a not-yet-initialized account would look like once initialized, without submitting a transaction.
- **Rosetta-RPC support** for both the `DeterministicStateInit` and `UniversalStateInit` actions, closing the gap noted in [Unresolved Issues](#unresolved-issues).
- **Consolidating the deterministic and universal state-init code paths.** The runtime handlers and validators for the two actions share most of their logic today by convention, not by a shared implementation; a follow-up refactor to fold them together (without changing the stable `0s` path's behavior) is intentionally deferred, to keep this feature's changes off that path.
- **External Contract Calls.** A related, separate proposal for sender-less transactions is expected to reuse the same uninitialized-account model and `is_initialized()` gate this proposal introduces, and to synchronize with self-signed initialization specifically.

## Consequences

### Positive

- One scheme, rather than three-going-on-four, for every future implicit and deterministic account, quantum-safe from day one.
- A contract built against this scheme can create and address `StateInit` versions defined after it was compiled, via the two new host functions, avoiding the forward-compatibility gap left open by [NEP-616]'s equivalent mechanism.
- No migration and no change to any existing account: NEAR-implicit, ETH-implicit, and `0s` deterministic accounts are entirely unaffected.
- Committing a post-quantum access key to a universal account costs the same as a classical one, since only its hash is ever stored.
- An uninitialized account is provably inert outside its own matching `StateInit`, which is what makes both supported creation flows (batched and self-signed) safe.

### Neutral

- `0s` and `0u` are two permanently coexisting, structurally disjoint schemes, not one scheme superseding the other.
- Access keys in a `StateInit` are full-access only for now; more restricted key kinds are deferred, not precluded.
- `StateInit`-content canonicity is a producer responsibility, not a protocol guarantee, a departure from the "one guaranteed encoding" assumption a reader might otherwise bring from other content-addressed schemes.
- No protocol-level checksum means a mistyped address is not rejected outright, only (almost certainly) nonexistent; this trades a stronger, unenforceable guarantee for a weaker, actually-safe one.

### Negative

- The protocol gains a third account state. Every path that reads an account, on chain and off, now has to distinguish "uninitialized" from both "nonexistent" and "initialized," where two states sufficed before.

### Backwards Compatibility

Universal accounts are fully additive. No existing account, address format, or action is changed; `0s`, ETH-implicit, and NEAR-implicit accounts and the actions that create them are untouched. `UniversalStateInit` is a new, disjoint action, gated behind its own protocol feature, and cannot be produced by, or collide in address space with, any pre-existing account kind.

## Unresolved Issues

- **Sharded-fungible-token re-derivation.** A vector equivalent to [Appendix A](#appendix-a-wallet-contract-re-derivation-vector), for sharded fungible token wallets, is deferred, pending that contract's own completion.
- **A distinct `UNINITIALIZED_ACCOUNT` RPC status**, and view-calls against a not-yet-initialized account with an optional state-init parameter, are both tracked as post-stabilization follow-ups, not yet implemented.
- **Rosetta-RPC support** for `DeterministicStateInit` and `UniversalStateInit` remains an open `TODO`, predating this proposal. The adapter matches both actions but emits no operations for either, so a Rosetta-based observer or indexer does not see universal-account creation or initialization at all.
- **Full de-duplication of the deterministic and universal state-init runtime code.** The two handlers and validators share logic by convention rather than by a shared implementation; consolidating them is deliberately deferred to a follow-up refactor to keep this feature's changes off the stable `0s` path.

## Appendix A: Wallet-contract re-derivation vector

This vector shows that an existing `0s` deterministic account's state is representable, byte-identically, under the `0u` scheme, without changing the contract or its data. It is not a migration: the `0s` account keeps its `0s` id; the `0u` id derived alongside it names a distinct, hypothetical account holding the same state under the new scheme.

The fixture is the ed25519 wallet contract from [near/intents](https://github.com/near/intents), read from its live mainnet deployment at [`0scdb6cfeed476fc878af9d3246768cbe803714c87`](https://nearblocks.io/address/0scdb6cfeed476fc878af9d3246768cbe803714c87). Its `DeterministicAccountStateInit` is rebuilt from the account's on-chain storage, with the two nonce fields the contract mutates as it is used reset to their initial, zero values, and checked to re-derive the `0s` id the account actually has on chain: the fixture is the deployed state, not a lookalike.

The same `code`, a reference to the wallet's global contract (`0sb0d7ef4f935c6ef78e08ad03569767aaec4223a3`), and `data`, the contract's one storage entry, carry over into a `UniversalStateInitV1` unchanged. `access_keys` is empty: this contract checks its owner's key itself, against a field in `data`, rather than relying on a protocol access key. That is the general convention for re-expressing a contract of this kind: a native access key belongs in `access_keys`; a contract-checked credential stays in `data`.

The canonical borsh of that `UniversalStateInitV1`, the exact bytes the `0u` id hashes, is:

```
00        UniversalStateInit::V1
01        code: Some
01        GlobalContractIdentifier::AccountId
2a000000  account id, 42 bytes: 0sb0d7ef4f935c6ef78e08ad03569767aaec4223a3
01000000  data: 1 entry
00000000  key: empty
3d000000  value, 61 bytes: the wallet's State<Ed25519PublicKey>
          (signature_enabled, subwallet_id, public_key, timeout,
          last_cleaned_at, nonces.old, nonces.current, extensions)
00000000  access_keys: none
```

which derives `0u4bfkw2qvgfzbf7zzkxykcppqymn0p2hbayjee3ygzrbhmmtyejx0`, distinct from the account's `0s` id, as expected for two disjoint schemes.

The vector, its full provenance, and the published hex are in `core/primitives/src/universal_state_init_vectors.rs`; `test_universal_state_init_wallet_contract_vector` reproduces the `0u` id on a running chain and checks the installed storage comes back byte-identical. (See [#16372](https://github.com/near/nearcore/pull/16372)).
