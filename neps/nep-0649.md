## Summary

With the introduction of [NEP-645], users got access to PQ transaction signatures on NEAR Protocol, allowing them to protect their accounts against a future quantum computer threat by adding an ML-DSA-65 access key. Meanwhile, self-custodial HD wallets, which serve as the main point of entry for users on NEAR, do not have a specification to follow on how to derive those keys deterministically.

[SLIP-10] specification does not yet cover ML-DSA and has an open PR ([slips#1968]) that proposes adding it.

This NEP specifies the standard on how wallets should deterministically derive ML-DSA-65 key pairs from a BIP-39 mnemonic using SLIP-10 hardened-only derivation, aligned with the construction proposed in [slips#1968].

## Motivation

The blockchain ecosystem is in early adoption stages of the post-quantum keys, and with introduction of ML-DSA-65 keys to NEAR Protocol users and wallets need a way to deterministically derive their access keys, similar to how it is done with Ed25519 keys specified in SLIP-10. This has several applications, for instance enabling key recovery from a [BIP-39] mnemonic alone, and cross-wallet portability.

Currently, there is only an open PR ([slips#1968]) that proposes a way to derive ML-DSA keys, but the timeline of its acceptance is not clear. Meanwhile, proprietary derivations are already appearing and the cost of not standardizing grows with every wallet that ships one.

## Specification

The keywords "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

### Overview

Wallet derives the binary seed from a [BIP-39] mnemonic and an optional passphrase. From that seed, the wallet derives a 32-byte node secret using `HMAC-SHA512` as specified in [SLIP-10] with key string `ML-DSA-65 seed`, following a hardened-only [BIP-44]-style path `m/44'/397'/account'` or `m/44'/397'/account'/change'/index'`, where `397'` is NEAR coin type specified in [SLIP-44]. This will result in a 32-byte node secret used as the seed for ML-DSA-65 key generation ([FIPS 204]), making the key pair usable on-chain as specified in [NEP-645] (gated by protocol feature `ProtocolFeature::PostQuantumSignatures`, active since protocol version 85).

### Scope

**In scope (this NEP):**

- ML-DSA-65 deterministic key derivation using 32-bytes output from SLIP-10 function with BIP-39 seed for Algorithm 6 `ML-DSA.KeyGen_internal(𝜉)` from FIPS 204.

**Out of scope:**

- Derivation for other ML-DSA key variants and a way to generate them (while possible, NEAR only enables ML-DSA-65).
- Derivation for other key types available for users on NEAR (Ed25519 and Secp256k1).
- Definition for non-hardened ML-DSA keys (see [Child Key Derivation](#child-key-derivation)).
- Post-derivation usage of the ML-DSA-65 keys by wallets (account discovery, key rotation).

### Derivation Path

This NEP adapts [BIP-44] paths. The coin type MUST be `397'`, which was assigned to NEAR in [SLIP-44]. Every level of the path MUST be hardened; this deviates from BIP-44, which defines the `change` and `index` levels as non-hardened.

- Wallets MUST support `m/44'/397'/account'`, where `account'` selects the key; the default path in this form is `m/44'/397'/0'`.
- Wallets MUST support a full BIP-44 path in the form `m/44'/397'/account'/change'/index'`; the default path in this form is `m/44'/397'/0'/0'/1'`.
- Wallets MAY support deeper BIP-44-style paths, with every level hardened. In this case, wallet MUST store the exact path and SHOULD display it to the user, since recovery in other wallets only checks two default paths (see [Recoverability](#recoverability)).

The two forms and their defaults mirror the existing Ed25519 path conventions on NEAR; note that the same mnemonic produces different keys at the two defaults, which is why recovery checks both shapes (see [Recoverability](#recoverability)).

Note that in the full form of the derivation path, `change'` carries no BIP-44 meaning: NEAR is account-based, so there is no distinction between external and internal addresses. The five-level shape is retained for compatibility with existing NEAR tooling (e.g. the Ledger app), and wallets are not expected to enumerate `change'` values.

The hardened-only requirement comes from ML-DSA itself, not from a design preference. Non-hardened derivation in [BIP-32] relies on the linear structure of elliptic-curve public keys: a child public key can be computed from the parent public key alone. ML-DSA has no such structure - key generation from FIPS 204 compresses the public key by dropping its low-order bits to save on key sizes, and this rounding is a lossy, non-linear operation that does not distribute over addition. Given only a rounded parent public key, the corresponding rounded child public key cannot be computed, so no analog of an extended public key exists for ML-DSA ([Lattice HD Wallets](https://eprint.iacr.org/2026/380)).

### Recoverability

Many wallets enable users to recover their accounts by deriving Ed25519 keys from the default path (commonly `m/44'/397'/0'`) with [BIP-39] mnemonic.

To ensure recoverability of the user's account with derived ML-DSA-65 keys:

- Wallets MUST accept any valid BIP-39 mnemonic (12-24 words) that the user entered for a recovery of existing keys.
- When recovering from a mnemonic, wallets MUST check both default paths - `m/44'/397'/0'` and `m/44'/397'/0'/0'/1'` - in both the Ed25519 and ML-DSA-65 trees.
- Wallets MAY generate a new BIP-39 mnemonic for ML-DSA-65 keys, at the cost of a second backup and loss of single-mnemonic recovery. However, newly generated BIP-39 mnemonics MUST be at least 18 words. See [Mnemonic as a security bottleneck](#mnemonic-as-a-security-bottleneck) for a reason behind that.

Account discovery is out of scope (see [Scope](#scope)). However, wallets that discover accounts via the existing Ed25519 flow are encouraged to check if the same seed phrase and default path specified in this section produce Ed25519 and ML-DSA-65 keys. Note that wallets might need to compute the ML-DSA-65 hash per [NEP-645] for discovering the account. Additionally, it is worth checking whether the key has `FullAccess` permission to enable full use of the account. 

### Master Key Generation

Master key derivation MUST follow the [SLIP-10] process described below.

The use of the node secret as key generation seed is specified in [Key Pair Generation](#key-pair-generation-fips-204).

Let S be a seed byte sequence of 128 to 512 bits. This is the same as the seed byte sequence used in BIP-32. The value of S MUST be the binary seed obtained from a [BIP-39] mnemonic and optional passphrase.

Let Key be the ASCII string used as the key for HMAC-SHA512 ([RFC 4231](https://datatracker.ietf.org/doc/html/rfc4231)), identifying the signature scheme; this is the string [SLIP-10] calls `Curve`, renamed here since ML-DSA is not an elliptic-curve scheme. This NEP defines derivation only for `Key = "ML-DSA-65 seed"`.

1. Calculate I = HMAC-SHA512(Key = "ML-DSA-65", Data = S)
2. Split I into two 32-byte sequences, I<sub>L</sub> and I<sub>R</sub>.
3. Use I<sub>L</sub> as master node secret, and I<sub>R</sub> as master chain code.

For ML-DSA, the last step always succeeds (note that there is no step 4 compared to [SLIP-10]), as any 32-byte sequence is a valid seed for the ML-DSA key generation.

### Child Key Derivation

Similar to Ed25519 and Curve25519 in SLIP-10, only hardened key derivation from private parent key to private child key is supported (see [Derivation Path](#derivation-path) for the reasoning).

The function CKDpriv((k<sub>par</sub>, c<sub>par</sub>), i) &rarr; (k<sub>i</sub>, c<sub>i</sub>) computes a child extended node secret from the parent extended node secret:

The function ser<sub>32</sub>(i) is defined in [BIP-32]: serialize a 32-bit unsigned integer i as a 4-byte Big-endian sequence.

1. Check whether i ≥ 2<sup>31</sup> (whether the child is a hardened key).
   - If so (hardened child): let I = HMAC-SHA512(Key = c<sub>par</sub>, Data = 0x00 || k<sub>par</sub> || ser<sub>32</sub>(i)). (Note: The 0x00 pads the node secret to make it 33 bytes long.)
   - If not (normal child): return failure.
2. Split I into two 32-byte sequences, I<sub>L</sub> and I<sub>R</sub>.
3. The returned child node secret k<sub>i</sub> is I<sub>L</sub>. The returned chain code c<sub>i</sub> is I<sub>R</sub>.

### Key Pair Generation (FIPS 204)

The ML-DSA-65 key pair is generated with Algorithm 6 `ML-DSA.KeyGen_internal(𝜉)` from [FIPS 204]. A 32-byte node secret I<sub>L</sub> from the [Child Key Derivation](#child-key-derivation) section MUST be used as a seed `𝜉` for `ML-DSA.KeyGen_internal(𝜉)`. At the same time, the 32-byte node secret from other [SLIP-10] key tree or any other private key MUST NOT be used as a seed `𝜉` for the ML-DSA-65 key generation. The resulting public key is a standard ML-DSA-65 public key and MAY be added to the user's account with the `AddKey` action as specified in [NEP-645].

On NEAR, the resulting key appears in two string formats:

- Public key string: `<key_type>:<base58-data>`, where `key_type` is `ml-dsa-65` and `base58-data` is the base58 encoding of the 1952-byte public key. This follows NEAR's convention for public key strings.
- On-trie handle: `<key_handle_type>:<base58-data>`, where `key_handle_type` is `ml-dsa-65-hash`, and `base58-data` is the base58 encoding of the 32-byte `SHA3-256(b"near:ml-dsa-65-pubkey-hash:v1" || public_key)` hash, as specified in [NEP-645]. This is the form returned by `view_access_key_list`, since the chain stores only the hash.

Usage of the 32-byte seed as the default key format is explicitly permitted by NIST in [Post Quantum FAQ](https://csrc.nist.gov/Projects/post-quantum-cryptography/faqs#Rdc7).

## Reference Implementation

The following Python implementation requires `bedrock-python` (the same library used to generate the [slips#1968] test vectors; its ML-DSA key generation is [tested against the NIST ACVP-Server KAT vectors](https://github.com/tectonic-labs/bedrock-python?tab=readme-ov-file#kats-vector-testing)) and `base58`.

```python3
#!/usr/bin/env python3

import hashlib
import hmac
import json
from dataclasses import dataclass

import bedrock_python as bedrock

# SLIP-0010 style seed modifier for HMAC-512
SEED_MODIFIER = b"ML-DSA-65 seed"
# BIP-32 hardened key offset: 2**31
HARDENED = 0x80000000
# NEP-645 public key domain to be used for hashing ML-DSA-65 public key with SHA3-256 to store on trie
MLDSA65_PUBKEY_DOMAIN = b"near:ml-dsa-65-pubkey-hash:v1"


# Master Key Generation
def master_node_derivation(seed: bytes, key: bytes) -> tuple[bytes, bytes]:
    if not 16 <= len(seed) <= 64:
        raise ValueError(
            f"Wrong seed: seed must be 128-512 bits (16-64 bytes), provided seed is {len(seed)} bytes"
        )

    I = hmac.new(key, seed, hashlib.sha512).digest()
    node_secret, chaincode = I[:32], I[32:]
    return (node_secret, chaincode)


# CKDpriv
def child_node_derivation(k_par: bytes, c_par: bytes, i: int) -> tuple[bytes, bytes]:
    assert len(k_par) == 32 and len(c_par) == 32

    if i < HARDENED:
        raise ValueError(
            f"Wrong index: non-hardened index {i} is unsupported for ML-DSA-65"
        )

    # Key
    k = c_par

    # Data
    d = b"\x00" + k_par + i.to_bytes(4, "big")

    I = hmac.new(k, d, hashlib.sha512).digest()
    node_secret, chaincode = I[:32], I[32:]
    return (node_secret, chaincode)


# Helper functions for ML-DSA-65 scheme
def mldsa_to_raw_bytes(key) -> bytes:
    """Extract raw bytes from ML-DSA key (verification key or signing key).
    bedrock-python serializes keys as JSON: {"scheme": 1, "value": "hex_string"}
    This function extracts the raw bytes from the 'value' field.
    """
    key_json = json.loads(key.to_string())
    return bytes.fromhex(key_json["value"])


def get_keypair(seed: bytes) -> tuple[bytes, bytes]:
    keypair = bedrock.MlDsaScheme.dsa_65().keypair_from_seed(seed)
    sk = mldsa_to_raw_bytes(keypair.secret_key())
    pk = mldsa_to_raw_bytes(keypair.public_key())
    return sk, pk


# Mnemonic helpers
def fmt_path(path: list[int]) -> str:
    display_path = "m"

    for i in path:
        display_path = display_path + "/" + str(i & (HARDENED - 1))

        if i >= HARDENED:
            display_path = display_path + "'"

    return display_path


def parse_path(path: str) -> list[int]:
    parts = path.split("/")
    assert parts[0] == "m"

    indices = []
    for part in parts[1:]:
        # Can be substituted with conversion of non-hardened index to hardened index.
        if not part.endswith("'"):
            raise ValueError(
                f"Wrong path: non-hardened index {part} is unsupported for ML-DSA-65"
            )
        indices.append(int(part[:-1]) + HARDENED)

    return indices


@dataclass
class DerivationNode:
    path: str
    node_secret: bytes
    chain_code: bytes
    private_key: bytes
    public_key: bytes

    @classmethod
    def from_node(cls, path: str, k: bytes, c: bytes) -> "DerivationNode":
        private_key, public_key = get_keypair(k)

        return cls(path, k, c, private_key, public_key)

    def to_dict(self) -> dict:
        return {
            "path": self.path,
            "node_secret": self.node_secret.hex(),
            "chain_code": self.chain_code.hex(),
            "private_key": self.private_key.hex(),
            "public_key": self.public_key.hex(),
        }


@dataclass
class TestVector:
    name: str
    mnemonic: str | None
    seed: bytes
    path: list[int]
    derivations: list[DerivationNode]

    @classmethod
    def generate(
        cls, name: str, mnemonic: str | None, seed: bytes, path: str
    ) -> "TestVector":
        indices = parse_path(path)
        k, c = master_node_derivation(seed, SEED_MODIFIER)
        derivations = [DerivationNode.from_node("m", k, c)]

        for depth, i in enumerate(indices, start=1):
            k, c = child_node_derivation(k, c, i)
            derivations.append(
                DerivationNode.from_node(fmt_path(indices[:depth]), k, c)
            )

        return cls(name, mnemonic, seed, indices, derivations)

    def to_json(self) -> dict:
        payload = {
            "name": self.name,
            "mnemonic": "" if self.mnemonic is None else self.mnemonic,
            "seed": self.seed.hex(),
            "full_derivation_path": fmt_path(self.path),
            "derivations": [d.to_dict() for d in self.derivations],
        }

        return payload


def main() -> None:
    vectors = [
        TestVector.generate(
            name="Test vector SLIP-0010 1",
            mnemonic=None,
            seed=bytes.fromhex("000102030405060708090a0b0c0d0e0f"),
            path="m/0'/1'/2'/2'/1000000000'",
        ),
        TestVector.generate(
            name="Test vector SLIP-0010 2",
            mnemonic=None,
            seed=bytes.fromhex(

            ),
            path="m/0'/2147483647'/1'/2147483646'/2'",
        ),
        TestVector.generate(
            name="Test vector NEP-649 1",
            mnemonic="orbit pill once attitude garbage prefer afford what banner weird path present dream tide unfold despair inject physical lens battle fancy finish fever toward",
```

## Security Implications

### Mnemonic as a security bottleneck

The derivation of an ML-DSA-65 key is deterministic end to end; hence, the key's security is capped by mnemonic entropy. Since the derivation algorithm is public, an attacker can enumerate candidate mnemonics, derive keys from each, and compare the results against on-chain data with the cost of 2<sup>entropy</sup> operations. For a key whose entire purpose is quantum resistance, the mnemonic should not be the component with the smallest quantum security margin.

[FIPS 204] assigns ML-DSA-65 to NIST Security Category 3. The table below maps [BIP-39] mnemonic length to its entropy and the effective security of the derived ML-DSA-65 key:

| Mnemonic length | Entropy bits | NIST Security Category of a key       |
| --------------- | ------------ | ------------------------------------- |
| 12 words        | 128          | NIST Category 1 (mnemonic limit)      |
| 18 words        | 192          | NIST Category 3                       |
| 24 words        | 256          | NIST Category 3 (scheme is the limit) |

Therefore, newly generated mnemonics MUST be from 18 to 24 words, as a mnemonic of fewer than 18 words provides less than 192 bits of entropy matching ML-DSA-65's Category 3 strength. Wallets MUST still accept any valid [BIP-39] mnemonic (12-24 words); the length limit only applies to generation.

### Sharing a mnemonic across key schemes

Deriving the ML-DSA-65 key from the same mnemonic as other key schemes does not compromise ML-DSA-65 security. All derivation steps are one-way: recovering the seed S - or any node secret - from a compromised child key requires inverting HMAC-SHA512, which is infeasible even for a quantum attacker. In particular, a future quantum attacker that recovers a user's Ed25519 private keys from their public keys gains no information about the ML-DSA-65 keys derived from the same mnemonic.

## Alternatives

### Waiting for SLIP-0010 to adopt ML-DSA upstream

The construction in this NEP is proposed upstream in [slips#1968]. Waiting for it to merge was considered, but rejected. The upstream review is unresolved not on the construction itself, but on where it should live: reviewers have questioned whether hardened-only schemes belong in SLIP-0010 at all, or in a new SLIP dedicated to NIST algorithms. Meanwhile, ML-DSA-65 keys are already on NEAR ([NEP-645], protocol version 85), and wallets that want to offer them must derive them somehow and leaving derivation schemes to individual wallets might create problems in the long-term.

### A distinct derivation path for post-quantum keys

Other ecosystems introduce a new purpose or coin type when adding a signature scheme (BIP-49/84/86), so that a bare mnemonic identifies the key type from the path alone. However, SLIP-0010's own model separates schemes by the `Key` string (which SLIP-0010 calls `Curve`) at the master key generation, making keys at identical paths cryptographically unrelated.

## Future possibilities

- Expanding the specification to other ML-DSA variants if it is required by a new NEP.

## Consequences

### Positive

- Wallets on NEAR have standardized way to derive ML-DSA-65 keys for users, aligned with [slips#1968] and [QIP-0002](https://github.com/Quantus-Network/improvement-proposals/blob/main/qip-0002.md).
- Reuses existing path convention on NEAR and SLIP-0010 specification, so wallets extend existing derivation code instead of adding a new stack.

### Neutral

- Derivation is Hardened-only, which is inherent to ML-DSA (see [Child Key Derivation](#child-key-derivation))
- The path does not identify the scheme, as scheme identity lives in the Key string. Wallets must treat the Ed25519 and ML-DSA-65 trees as independent and scan both trees at both default paths during recovery (see [Recoverability](#recoverability)).
- Wallets with pre-existing proprietary ML-DSA derivations face a one-time key rotation to become compliant (covered in [Backwards Compatibility](#backwards-compatibility)).

### Negative

- If [slips#1968] merges in modified form, NEAR is permanently locked to this construction (see [Backwards Compatibility](#backwards-compatibility) below).
- Recovery becomes more expensive: a bare-mnemonic recovery must derive and check several candidate keys - two trees (Ed25519 + ML-DSA-65) at two default paths each - instead of one.

### Backwards Compatibility

This NEP is an off-chain wallet standard. It introduces no protocol changes, no new on-chain types, and no changes to how existing keys behave once added to an account - all of that is defined by [NEP-645]. Derivation of the classical key types is likewise unaffected: the Ed25519 tree and ML-DSA-65 tree are separated at the master key generation, so this NEP cannot change any key an existing wallet derives. In that regard, the NEP is backwards compatible.

However, two compatibility risks are worth mentioning:

- **Wallets that already ship a proprietary ML-DSA-65 derivation** will derive different keys from the same mnemonic than this standard. Those keys remain valid on-chain, but a compliant wallet will not re-derive them during recovery. Migration is a standard key rotation: add key derived as specified by this NEP using `AddKey` action, then remove the legacy key using `DeleteKey` action.
- **Upstream PR to SLIP-0010 might be merged in modified form**, or as a different SLIP. In that case, it might be better for wallets to disregard new SLIP standard and continue using the standard specified by this NEP, as derived keys cannot be re-derived under different parameters without breaking recovery of existing accounts.
