## Summary

This standard defines a one-byte, four-valued state that a contract uses when evidence from several sources (oracles, solvers, signers, cross-shard callbacks) disagrees. Instead of calling `env::panic_str()` or keeping only the last value written, the contract records the disagreement as `BOTH` (`0x03`), blocks side-effects that depend on it, keeps the work already done, and emits an NEP-297 event. Evidence is combined by one rule, the *chain meet*: the minimum on the total order `FALSE < NEITHER < BOTH < TRUE`. Because `TRUE` is the top of that order, no combination containing a non-`TRUE` value can ever produce `TRUE`, so only unanimous agreement authorises settlement. The interface is three view-compatible methods, needs one byte of state, allocates nothing and is `no_std` compatible.

## Motivation

Contracts that consume more than one source of truth face disagreement routinely: two price feeds differ, two solvers submit conflicting proofs for an intent, signers issue opposing directives, or an asynchronous callback returns a result that contradicts the caller's pending state. Today a contract has three options, and each loses something:

1. **Panic.** The receipt fails, its gas is spent, and the only record of the disagreement is a string.
2. **Last writer wins.** Earlier evidence is discarded silently, and the outcome depends on submission order.
3. **Wait.** Downstream automation stalls with no defined state to observe.

There is no shared way to say *"these sources disagree: hold the funds, keep the evidence, do not revert"*. Each project invents its own encoding, so indexers, wallets, agents and auditors cannot recognise contention across contracts. A standard state with a standard event makes the failure mode defined, observable and recoverable, and lets agents and solver networks interoperate on the same semantics.

## Specification

### States

| Name | Value | Meaning | Side-effects |
|---|---|---|---|
| `NEITHER` | `0x00` | No evidence yet | Blocked |
| `TRUE` | `0x01` | Agreed and attested | **Allowed** |
| `FALSE` | `0x02` | Explicitly refuted | Blocked |
| `BOTH` | `0x03` | Conflicting evidence, held | Blocked, **not reverted** |

Any byte above `0x03` is invalid input and MUST be treated as `NEITHER` (fail closed).

### Order and the chain meet

The total order is `FALSE < NEITHER < BOTH < TRUE`, encoded by the rank table `RANK = [1, 3, 0, 2]` indexed by state value. The meet of two valid states is the one with the lower rank. The meet of a list is the left fold of the pairwise meet over the list; the meet of an empty list is `NEITHER`.

| meet | NEITHER | TRUE | FALSE | BOTH |
|---|---|---|---|---|
| **NEITHER** | NEITHER | NEITHER | FALSE | NEITHER |
| **TRUE** | NEITHER | TRUE | FALSE | BOTH |
| **FALSE** | FALSE | FALSE | FALSE | FALSE |
| **BOTH** | NEITHER | BOTH | FALSE | BOTH |

The meet is idempotent, commutative and associative, so the result does not depend on the order in which evidence arrives.

**Invariant:** the meet of a non-empty list is `TRUE` if and only if every element is `TRUE`.

How a contract maps its own evidence to states is outside this standard; a typical mapping is: a source that agrees is `TRUE`, a source that refutes is `FALSE`, a source that has not reported is `NEITHER`, and a pair of sources that report incompatible values is `BOTH`.

### Interface

A conforming contract exposes:

```rust
pub trait PanicFreeResolution {
    /// The chain meet of `inputs`. Returns 0x00..=0x03.
    /// Invalid bytes fail closed to NEITHER; an empty slice returns NEITHER.
    fn nep_conjoin(&self, inputs: Vec<u8>) -> u8;

    /// True if and only if `state == 0x01`.
    fn nep_is_settleable(&self, state: u8) -> bool;

    /// A human-readable statement of the invariant.
    fn nep_invariant(&self) -> String;
}
```

All three methods MUST be callable as view functions and MUST NOT write state.

### Behaviour at a decision point

When a contract reaches a decision that depends on contention-prone evidence, it MUST:

1. compute the meet of the evidence;
2. perform the dependent side-effect (transfer, release, state change) only if `nep_is_settleable` returns `true`;
3. otherwise keep any escrowed value where it is, record the resulting state, and emit the event below;
4. not revert work already committed in earlier receipts because of a non-settleable result.

How contention is later resolved (an arbitration oracle, a governance vote, a timeout with refund) is a contract design choice and is outside this standard.

### Event

On entering `BOTH`, a contract SHOULD emit an NEP-297 event:

```
EVENT_JSON:{"standard":"nep-panic-free-resolution","version":"1.0.0","event":"contention_held","data":[{"state":3,"subject":"<contract-defined id>","evidence":["<receipt or source hash>", "..."]}]}
```

On leaving a held state it SHOULD emit `contention_resolved` with the final state.

## Reference Implementation

A minimal implementation:

```rust
const RANK: [u8; 4] = [1, 3, 0, 2]; // indexed by NEITHER, TRUE, FALSE, BOTH

pub fn meet(a: u8, b: u8) -> u8 {
    if a > 3 || b > 3 { return 0; }
    if RANK[a as usize] <= RANK[b as usize] { a } else { b }
}

pub fn conjoin(inputs: &[u8]) -> u8 {
    let mut it = inputs.iter();
    let Some(&first) = it.next() else { return 0 };
    if first > 3 { return 0; }
    it.fold(first, |acc, &v| if v > 3 { 0 } else { meet(acc, v) })
}

pub fn is_settleable(state: u8) -> bool { state == 1 }
```

Note that once an invalid byte has produced `NEITHER`, later inputs can only keep or lower the result, never raise it to `TRUE`.

Tests that a conforming implementation should pass: `FALSE` dominates; `BOTH` with `TRUE` is `BOTH` and not settleable; `TRUE` with `TRUE` settles; `NEITHER` with `BOTH` is `NEITHER`; empty input is `NEITHER`; any byte above 3 fails closed; of the 16 ordered pairs, only `(TRUE, TRUE)` meets to `TRUE`; associativity over all 64 triples.

Live deployments implementing these semantics on NEAR mainnet (view calls are free):

- `f18889ea8bc108de53b899df3a3417c76995cbb55fb2174ff08d2e0abee99bcf` — `is_settleable{"state":"BOTH"}` returns `false`, `{"state":"TRUE"}` returns `true`.
- `scp144.near` — `conjoin{"inputs":[1,2]}` returns `FALSE`, `[1,3]` returns `BOTH`, `[0,3]` returns `NEITHER`.

These use string names and a slightly different method naming from the interface above; a conforming wrapper is straightforward. A Rust crate (`near-panic-free`) and examples are in `https://github.com/sykomiked/zxv-nep-submission`.

## Security Implications

- **Funds held indefinitely.** A held state blocks release. Contracts MUST provide a resolution path (arbitration, timeout refund or governance), or funds can be stuck. This standard does not define one.
- **Griefing.** A single dissenting source can force `BOTH`. Contracts should choose their evidence sources and their arbitration rules with this in mind, and may require bonds from reporters.
- **Unbounded evidence.** Contracts MUST bound any stored evidence list (a fixed-size ring or a rolling hash) to avoid storage exhaustion.
- **Invalid input.** Out-of-range bytes fail closed. Implementations must not use a bitwise join such as `(a | b) & 3`, which can return `TRUE` for invalid input.
- **Not a consensus mechanism.** The meet only combines states already produced; the security of the result depends entirely on how each source's state is established.

## Alternatives

- **Panicking on disagreement.** Simple, but it discards the evidence, spends the gas and gives downstream systems nothing to observe.
- **Last writer wins.** Keeps liveness but loses evidence and makes outcomes depend on submission order, which can be manipulated.
- **Belnap–Dunn four-valued logic (FOUR).** Uses the same four values on a bilattice, but there `BOTH OR NEITHER = TRUE`, so a combination of non-`TRUE` values can yield `TRUE`. For an authorisation gate the single chain is safer and reduces to one comparison.
- **Majority voting.** Useful as an arbitration rule, but it hides the disagreement rather than recording it; it can be layered on top of this standard.

## Future possibilities

- Additional phases above `0x03` with their own ranks, extending the order without changing the one-byte interface.
- Wallet and explorer support for displaying held states and their evidence.
- A companion standard for arbitration requests and responses.
- If adoption is broad, a host function for the meet, though its cost is already negligible.

## Consequences

### Positive

- One recognisable way to represent and observe contention across contracts.
- No lost work or evidence on disagreement; predictable, very low cost.
- A structural guarantee that only unanimous agreement settles.

### Neutral

- Contracts still choose how evidence maps to states and how contention is resolved.

### Negative

- Contracts must handle a held state explicitly; code written to expect reverts needs changes.
- A poorly designed resolution path can lock funds.

### Backwards Compatibility

The standard is additive. Existing contracts are unaffected unless they adopt it; adopting it adds one byte of state and three view methods.
